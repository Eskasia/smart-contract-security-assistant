# v0.2.0 Release Readiness Checklist

Status: release readiness draft

https://github.com/Eskasia/smart-contract-security-assistant/releases/tag/v0.1.0

## Release Goal

Publish the evidence platform update as `v0.2.0`, covering the HTTP/API/frontend
flow plus the Evidence Graph, Phase 3 advanced evidence, SBOM/license clarity,
and benchmark/eval gates now merged into `main`.

## Version Decision

Use `v0.2.0`, not `v0.1.1`, because the merged work adds new reviewer-facing
platform capabilities:

- HTTP API and React/Vite reviewer workbench from PR #15.
- Evidence Graph, standards mapping, native rules, and provenance UI from
  PR #16.
- Sandbox-only exploit validation, fuzz seed suggestions, formal property
  drafts, DeFi profit signal, and EVMbench adapter gates.
- Third-party notices, license-boundary docs, tool attribution, and generated
  SBOM/license inventory workflow.
- Expanded backend, frontend, benchmark, and documentation validation gates.

## Release Candidate Checks

Run from a clean `main` checkout before tagging:

```bash
git pull origin main
uv run ruff check .
uv run pytest
uv run python scripts/check_tool_matrix.py
cd frontend && npm run test -- --run
cd frontend && npm run build
git diff --check
git status
```

Expected minimum results:

```text
ruff: all checks passed
pytest: 116 passed
tool_matrix and standards_mapping checks passed
frontend test: 35 passed
frontend build: completed
git diff --check: passed

```

## Release Notes Must Include

- v0.1.0 was the first public OSS quickstart release.
- v0.2.0 adds the evidence platform layer: HTTP/API/frontend reviewer flow,
  Evidence Graph, standards mapping, native rules, and advanced evidence records.
- Phase 3 advanced evidence remains reviewer-facing and sandbox-only where
  applicable; it does not replace human audit or prove exploitability by itself.
- Python and npm dependency licenses are covered by generated SBOM/license
  inventory artifacts; external security-tool notices are tracked separately.
- Validation result: `116 passed` for backend tests and `35 passed` for frontend
  tests on 2026-06-01.

## Tester Feedback Issue Handling

Keep issue #12 as the v0.1.0 tester feedback issue because it links to the
published v0.1.0 release and its original quickstart scope.

For v0.2.0, open a new tester feedback issue after the release candidate is
ready, or add a maintainer comment to issue #12 that points testers to the new
v0.2.0 release issue. Do not rewrite the historical v0.1.0 issue body as if it
had always targeted v0.2.0.

## GitHub Release Steps

1. Confirm `main` is up to date and CI is passing.
2. Confirm README, CHANGELOG, release checklist, and tester-feedback wording are
   consistent with `v0.2.0`.
3. Merge the release readiness PR.
4. Tag the verified main commit:

   ```bash
   git tag v0.2.0
   git push origin v0.2.0
   ```

5. Create the GitHub release from the tag.
6. Paste release notes from `CHANGELOG.md` and this checklist.
7. Re-check the rendered GitHub README and release page.

## Do Not Include

- Generated report folders unless explicitly required as release artifacts.
- `新修改方向1.0.0/` or other local roadmap scratch folders.
- Private keys, secrets, customer data, proprietary contracts, or unpublished
  third-party audit material.
- Claims that SCSA replaces manual audit or external security tools.
